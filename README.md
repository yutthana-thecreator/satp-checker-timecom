# SATP Checker — TIME.com Project

ระบบตรวจเอกสาร acceptance ของโปรเจกต์ TIME.com (AGRID 2.0 / DC2DC) สำหรับทีม Nokia Field Service

เว็บตรวจเอกสาร SATP + Attachment Report (TIME DWDM / Nokia 1830) — ทำงานในเบราว์เซอร์ทั้งหมด ไฟล์เอกสาร**ไม่ถูกส่งออกจากเครื่องผู้ใช้** Vercel ทำหน้าที่แจกหน้าเว็บอย่างเดียว

## ใช้งาน
1. เปิดหน้าเว็บ → ลากไฟล์ PDF / zip / โฟลเดอร์ไซต์มาวาง (ต่อไซต์ = SATP 1 + Attachment 1)
2. กด **ตรวจเอกสาร** → ตรวจ 3 ส่วนอัตโนมัติ: ข้อความ (ทันที) → OCR screenshot (O01–O06) → รูปถ่าย (เทียบรูปอ้างอิง + อ่านป้าย) ทีละไซต์ในพื้นหลัง สถานะ "ผ่าน (ยังไม่ตรวจ OCR/รูป)" → "(ยังไม่ตรวจรูป)" → "รอ ROM ตรวจรูป N" หรือ "ผ่าน" · ป้ายแท็บบอกผลแต่ละส่วน เช่น "ประเด็น (5) · ตรวจรูป: รอ ROM 4 · OCR screenshot: ข้อสังเกต 5" คลิกไซต์เพื่อดูประเด็น (ระดับ 1 ครบถ้วน / 2 สอดคล้อง / 3 ค่าทางเทคนิค พร้อมหน้า-section) · สถานะรวม = ข้อความ + รูป ผ่านต่อเมื่อทั้งสองส่วนผ่าน
3. แท็บ **ตรวจรูป** → กด Accept / Reject ทีละรูป (Reject ต้องเลือกเหตุผล) ระบบช่วยแจ้งรูปซ้ำ/เบลอ
4. **ดาวน์โหลด Excel** → ชีท สรุป · ประเด็น (รวมผลเดิมก่อน ROM ตัดสิน, การตัดสินใจ, ขอบเขต, เหตุผล, โดย, เมื่อ) · ตรวจรูป (Accept อัตโนมัติ/ROM, Reject, เหตุผล) · ข้อมูลไซต์ · Inventory (การ์ด/serial จาก OCR) — สร้างสด ณ ตอนกด ตัดสินใจเพิ่มแล้วต้องกดดาวน์โหลดใหม่
5. ปุ่ม **เกณฑ์ตรวจ** แก้ค่าเกณฑ์ได้ (เก็บในเบราว์เซอร์เครื่องนั้น) ค่าว่าง = ไม่ตัดสิน

ประวัติการตรวจและผล Accept/Reject เก็บใน localStorage ของเบราว์เซอร์เครื่องนั้นเท่านั้น

## ระบบเรียนรู้จากการตัดสินใจของ ROM (ฐานความรู้)
สิ่งที่ระบบตัดสินเองไม่ได้จะมีปุ่มให้ ROM ตัดสิน และผลถูกเก็บเป็นข้อมูลอ้างอิงสำหรับครั้งต่อไป:
- **ประเด็น** (เตือน/ข้อมูล หรือที่ระบุ "คนตรวจ/ROM/CPM") → ปุ่ม *ยอมรับ* / *ยืนยันปัญหา* + เหตุผล — ประเด็นชนิดเดียวกัน (กฎ+section+ประเภท+โปรไฟล์+ข้อความที่ตัดตัวเลข/รหัสไซต์ออก) ในไซต์ต่อไปจะถูกติดป้าย "ยอมรับแล้ว" อัตโนมัติและไม่นับเป็นเตือน
- **ไซต์ที่ไม่ตรงโปรไฟล์ใด** → ปุ่ม *ROM ยืนยัน: ใช้ไซต์นี้เป็นอ้างอิง* → บันทึกเป็นโปรไฟล์ใหม่ L1, L2, … (config + ค่าที่วัด) ไซต์ต่อไปที่ config เดียวกันจะจับคู่โปรไฟล์นี้และนับตัวอย่างเพิ่ม
- **รูป** → Accept = เก็บรูปย่อเป็นรูปอ้างอิงของ (โปรไฟล์ × section) แสดงเทียบข้างรูปใหม่ (สูงสุด 3 รูป/หัวข้อ) · Reject = จำ hash + เหตุผล ถ้ารูปเดิมโผล่อีกจะเตือน
- ฐานความรู้ซิงก์กับ Supabase ของทีม (สำเนาในเครื่องอยู่ใน localStorage + IndexedDB)

## แท็บประเด็น: ดูจุดที่พบและการตัดสินใจของ ROM
- คอลัมน์ "หน้า" เป็นปุ่ม กดแล้วแสดงหน้าเอกสารจริง (SATP หรือ Attachment ตาม section) พร้อมไฮไลต์ข้อความที่พบ (ข้อความใน '…' ของประเด็น หรือ IP / slot / ตัวเลข) เลื่อนหน้า ◀ ▶ ได้ ถ้าจุดผิดอยู่ในรูป/ตารางที่ไม่มีข้อความ จะแสดงหน้าโดยไม่ไฮไลต์
- แถว **เตือน**: ยอมรับ / ยืนยันปัญหา → ระบบเรียนรู้ใช้กับประเด็นชนิดเดียวกันทุกไซต์
- แถว **ไม่ผ่าน**: ปุ่ม "ยอมรับ (ไซต์นี้)" + เหตุผล → มีผลเฉพาะไซต์และหน้านั้น (key `S:<ไซต์>|<หน้า>|<ลายเซ็น>` ในฐานความรู้) ระบบไม่นำไปใช้กับไซต์อื่น ประเด็นกลายเป็น "ข้อมูล (เดิม fail)" และสถานะไซต์คำนวณใหม่ · ปุ่ม "ยกเลิก" คืนค่าเดิม

## ฐานความรู้ร่วมของทีม (Supabase)
ฐานความรู้ซิงก์กับ Supabase project `satp-checker-timecom` โดยไม่ต้อง login (ตัดสินใจโดยผู้ใช้ 2026-09-29) — ใครที่รู้ URL เว็บก็อ่าน/เขียนได้ ถ้าต้องการจำกัดให้เปิด Password Protection ของ Vercel
ตั้งค่าครั้งแรก: รัน `supabase/schema.sql` แล้วตามด้วย `supabase/no-login.sql` ใน SQL Editor · ใส่ Project URL + publishable key ใน `src/config.js`
(ถ้าภายหลังต้องการบังคับ login: ลบ policy `kb_anon`/`thumbs_anon_*` แล้วเปิดใช้ magic link ตามโค้ดเดิมใน git history)

สิ่งที่ขึ้นคลาวด์: การตัดสินใจประเด็น, ผล Accept/Reject (hash), โปรไฟล์ที่เรียนรู้, รูปย่ออ้างอิง (~30 KB/รูป), สถิติจำนวนรูปต่อหัวข้อ — ไฟล์ PDF และรูปเต็มไม่ออกจากเครื่อง
ทุกการตัดสินใจใหม่ขึ้นคลาวด์ทันที เปิดหน้าเว็บ/กด "ซิงก์" จะดึงของทีมลงมา ปุ่ม "อัปโหลดฐานความรู้ในเครื่องขึ้นคลาวด์" ใช้ย้ายข้อมูลเดิมครั้งแรก (ปุ่มส่งออก/นำเข้า JSON และล้างฐานความรู้ถูกถอดออกแล้ว ฟังก์ชัน exportKb/importKb ยังอยู่ใน learn.js)

## รูปอ้างอิง (reference photos) และการตัดสินรูปอัตโนมัติ
ระบบเก็บรูปอ้างอิงต่อ (โปรไฟล์ × หัวข้อ เช่น "1.8 (a) Rack Installation") พร้อมจำนวนรูปต่อหัวข้อ จาก 3 แหล่ง:
- **ลูกค้าเซ็นแล้ว** (`signed`) — ไฟล์ที่มี Acceptance Date หรือ `_Signed` เก็บอัตโนมัติตอนตรวจ
- **ตัวอย่าง** (`sample`) — ปุ่ม "ใช้ทุกไซต์ในชุดนี้เป็นรูปอ้างอิง" ในผลตรวจ (ROM ยืนยันว่ารูปชุดนั้นถูกต้อง) · ชุดเริ่มต้นคือ 46 ไซต์ AGRID/DC2DC = 1,829 รูป
- **ROM Accept** (`rom`) — รูปที่ ROM กด Accept เก็บล่าสุด 3 รูปต่อหัวข้อ

**ลายเซ็นภาพ**: ทุกรูปอ้างอิงถูกแปลงเป็นเวกเตอร์ 512 ค่า (CLIP ViT-B/32 รันในเบราว์เซอร์ผ่าน transformers.js, โมเดล ~90 MB โหลดครั้งแรกแล้ว cache) เก็บใน Supabase คู่กับรูปย่อ การเทียบรูปใหม่ใช้เวกเตอร์เท่านั้น ไม่ต้องดาวน์โหลดรูปย่อทั้งชุด (ดาวน์โหลดเฉพาะ 3 รูปที่คล้ายที่สุดของรูปที่ต้องให้ ROM ดู)

**กฎตัดสินในแท็บตรวจรูป** (`src/app.js` reviewPanel):
1. รูปใหม่ → เวกเตอร์ → หาความคล้ายสูงสุดกับรูปอ้างอิงหัวข้อเดียวกัน (s1) และกับ section อื่น (so) ไม่นับรูปของไซต์ตัวเอง
2. เกณฑ์ต่อหัวข้อ = p10 ของความคล้าย leave-one-site-out ของรูปอ้างอิงเอง (อย่างน้อย `imageSim.value` 0.70 สูงสุด 0.90; หัวข้อที่มี < 8 รูปใช้ 0.78) — screenshot ได้เกณฑ์ ~0.92 รูปถ่ายกราวด์/ODF ~0.72
3. **ผ่านอัตโนมัติ** เมื่อ s1 ≥ เกณฑ์ และ s1 + `margin` (0.03) ≥ so และไม่มีธง (รูปซ้ำ, นำรูปไซต์อื่นมาใช้, เบลอ, เคยถูก Reject, คล้ายรูปที่เคย Reject ≥ 0.95) → บันทึกเป็น Accept โดย "ระบบ" (ROM กด Reject ทับได้)
4. ไม่เข้าเกณฑ์ → อยู่หมวด "ต้องให้ ROM ตรวจ" พร้อมเหตุผลและรูปอ้างอิงที่คล้ายที่สุด 3 รูป
5. คาลิเบรตบน 1,829 รูป: ผ่านอัตโนมัติ 92% · รูปที่วางผิด section ถูกจับ 96% · รูปที่วางผิดหัวข้อย่อยใน 1.8 เดียวกันส่วนใหญ่ผ่าน (แจ้งเป็นหมายเหตุ "คล้ายหัวข้อ X มากกว่า")

ROM ถอดรูปอ้างอิงที่ไม่เหมาะออกได้ (ปุ่ม ×) มีผลทั้งทีม · `window.satpTest.backfillEmbeddings()` บน localhost ใช้เติมลายเซ็นให้รูปอ้างอิงเก่าที่ยังไม่มี

**อ่านป้ายในรูปถ่าย (OCR)** — `src/engine/labels.js` (รูปแบบป้ายจากเอกสาร TIME_AGRID2.0_DWDM_NOKIA_LABELLING FORMAT ON SITE Rev 0) + `ocrLabels()` ใน `src/ui/ocr.js`
- ทำกับรูปหัวข้อ 1.8 (a)(b)(c)(d)(e)(f)(g) และ 1.6 Ground: หาบริเวณเทปสีเหลือง (ป้ายของโปรเจกต์) ตัดออกมาขยาย 4 เท่า เพิ่ม contrast แล้ว OCR ทีละป้าย (ถ้าไม่พบสีเหลืองจึง OCR ทั้งรูปแบบ sparse) ~2.5 วินาที/รูป ผลถูก cache ต่อรูป
- ตัดข้อความ "TIME:<ไซต์>" ของแอปกล้อง Timemark ออกก่อน เพื่อไม่ให้นับเป็นป้าย
- เทียบ: รหัสไซต์ 5 ตัว (ยอมผิด 1 ตัวอักษร), ชื่อ NE `<ไซต์>_<ILA|RDM|EILA>_<เลข>`, IP บนป้าย vs หน้า 1, รหัสไซต์ปลายทางจากตาราง Span Loss (ป้าย TX:/RX:/FDF), โปรเจกต์
- ธง (ต้องให้ ROM ดู): ป้ายระบุไซต์อื่นที่ไม่ใช่ตัวเองหรือปลายทาง · IP บนป้ายไม่ตรงหน้า 1 · (b) NE ID ไม่พบรหัสไซต์บนป้าย · ป้าย DC2DC ในเอกสาร AGRID
- หมายเหตุ (ไม่กั้นการผ่าน): ไม่พบรหัส/คำสำคัญในหัวข้ออื่น (รูป power breaker ในเอกสารมักเล็กเกินอ่าน)
- ป้ายในรูป (a)/(b) ยืนยันรหัสไซต์ (+IP) = ผ่านอัตโนมัติแม้ความคล้ายภาพต่ำ เพราะเป็นหลักฐานตรงกว่า

## OCR screenshot (แท็บ "OCR screenshot" ต่อไซต์)
ใช้ Tesseract.js ในเบราว์เซอร์ (โหลดโมเดลจาก CDN ครั้งแรก ~10 MB แล้ว cache) ขยาย screenshot เป็น ~2,800 px ก่อนอ่าน (screenshot จอเต็มตัวอักษรในตารางสูง ~8 px ถ้าไม่ขยายอ่านชื่อการ์ดไม่ได้) ใช้เวลา ~5–7 วินาที/รูป:
- O01 Inventory: การ์ดตามโปรไฟล์, จำนวน shelf, วันที่-เวลา PC
- O02 Power: ค่าแรงดันในรูป vs ตาราง 1.5 (ข้อมูลเท่านั้น — อ่านตัวเลขบนรูปได้จำกัด)

- O04 ป้าย NE ID: มีรหัสไซต์
- O05 Fiber scope: PASS/FAIL และชื่อรายงานครอบคลุม LINE IN/OUT ทุกไซต์ปลายทาง
- O06 Block Diagram: ชื่อ NE และไซต์ปลายทางตรงตาราง Span Loss

- O09 ผังการ์ดต่อ shelf/slot vs ไซต์ตัวอย่างโปรไฟล์เดียวกัน (เรียนรู้จาก inventory ของทุกไซต์ที่เคยตรวจ ใช้เมื่อมี ≥ 3 ไซต์) — การ์ดอยู่ slot ที่ตัวอย่างไม่มี หรือขาดการ์ดที่ตัวอย่าง ≥ 70% มี
